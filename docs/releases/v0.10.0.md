# v0.10.0 — Canonical catalog 与 serving 证明

v0.10.0 更新 models.dev 数据来源，并进一步明确模型内禀能力、实际 serving 配置和可选推理档位分别需要什么证据。它延续 v0.9.0 的可信发布门禁，不重复说明 withheld、partial availability 或自动恢复等既有能力。

## 用户可见变化

- **使用 canonical catalog**：Pi 默认从 https://models.dev/catalog.json 获取 catalog.models canonical registry 与 catalog.providers serving 记录。两个部分来自同一份快照。
- **能力值按证据来源裁决**：canonical identity 经精确证明后，registry 才能提供模型内禀事实；serving 值还需要运维者显式声明 models_dev_provider，并且模型 wire id 精确命中该 provider 记录。只有关系指向 canonical model、但没有精确 SKU 的记录，不会作为 serving 证明。
- **不从无关记录猜测能力**：未证明的 provider、同名模型和变体只作为诊断候选。serving 记录缺少某字段时不再从 canonical 值回填；同维度的 LiteLLM 声明可以补缺，否则结果保持 unknown。非价格 litellm_params（如 max_tokens、reasoning_effort）表示 operator configuration，不证明 endpoint 实际执行该限制，也不生成模型能力或推理档位。
- **推理档位需要 serving 证明**：可选 thinking levels 来自已证明 serving 记录的 reasoning_options。没有精确 serving 证明时，档位状态为 unknown，Pi 不会展示可选档位；LiteLLM 的 reasoning_effort 声明本身不会创建档位。
- **LKG 使用 schema 8 group-wide proof**：v8 将整组 deployment 证据绑定到通过发布门禁的同一 resolution，恢复时整体重证、整体恢复或 fail closed，不会跨记录拼接字段。v7 或更早的条目 fail closed；catalog 恢复后的下一次 live discovery 会自动捕获 v8。若 catalog 在捕获前不可用，旧条目不会恢复。

例如，DeepSeek 输出上限采用 canonical 值 384000；只有精确 serving 证明成立时，provider serving 值才可能覆盖它。kimi-k3 的输出上限采用 canonical 131072，不会把未证明的一方 serving 值 1048576 当成内禀能力。

## 升级

Pi 没有新增配置项，也不需要迁移 endpoint 或凭据。若 models.dev 暂不可用，模型是否继续由 LiteLLM 声明完整性与兼容的 v8 LKG 证据决定；未证明或信息不足的模型仍按诊断结果处理。
